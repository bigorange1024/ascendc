## 1. 数学与数据契约（与实现无关）

### 1.1 我们在哪个域里算

Kyber / ML-KEM 类方案里，大量运算在 **模 q 的多项式环** 上进行，且常用 **NTT 域** 表示：

- 时域多项式 \(s, e, \ldots\) 经正向 NTT 得到 \(\hat{s}, \hat{e}, \ldots\)（系数仍在 \(\mathbb{Z}_q\) 语义下，实现上是 int32 向量）。
- **NTT 域中的「乘法」** 不是逐系数相乘，而是 **paired Cooley–Tukey 块上的 basemul**（本仓库 Alg.11/12）：每对相邻系数 \((a_{2i}, a_{2i+1})\) 与 \((b_{2i}, b_{2i+1})\) 经 \(\gamma_i\) 合并为 NTT 意义下的积。

因此：**「内积」在 NTT 域 = 多次 basemul + 系数维上的累加 + 最终模 q**」，不是普通点积。

### 1.2 行 18 类内积（矩阵–向量，NTT 域）

对行索引 \(p\)、列索引 \(j\)（本问题中 \(K=4\)）：

\[
\hat{t}[p] \;=\; \mathrm{mod}_q\!\left(\sum_{j=0}^{K-1} \widehat{A[p,j]} \circ \hat{s}[j]\right)
\]

其中 \(\circ\) 表示 **NTT 域多项式乘**（整 poly 长度 \(N\)，非 half-NTT 块内乘法的简单拼接）。

**与加解密的关系**：

- **封装 / KeyGen** 侧：多次「常数矩阵 × 秘密向量」或「向量 + 噪声」同属此结构；\(K\)、\(N\)、\(q\) 变，**累加–模约简结构不变**。
- **解密** 侧：invNTT 之前往往仍在 NTT 域做类似乘加；不要把「NTT 链结束」和「内积结束」混为一谈——中间态仍是 \(\hat{\cdot}\)。

### 1.3 何时 mod、何时 lazy

| 运算 | 典型策略 | 原因 |
|------|----------|------|
| 单次 basemul 内部 | **必须**在块内 Barrett / 等价约简 | 积的度数翻倍，不约简会溢出语义 |
| 对 \(j\) 的累加 \(\sum_j\) | 可用 **int64 累加，最后一次性 \(\mathrm{mod}_q\)** | 减少约简次数；\(K\) 小、\(q\) 固定时安全 |
| 加噪声 \(\hat{e}\) 之后 | **最终 \(\mathrm{mod}_q\)** | 与参考实现 golden 对齐 |

**工程推论**：验证时可拆成 **仅 \(\widehat{A}\cdot\hat{s}\)**（无 \(\hat{e}\)）与 **完整行 18** 两层 golden，对应「先验证乘法累加正确，再验证加噪声」。

### 1.4 布局是数学对象的索引约定

\(\widehat{A}[p,j]\) 是二维族的多项式。选定 **行主序**：

\[
\mathrm{flat}(p,j,c) = (p\cdot K + j)\cdot N + c
\]

与 **列主序** 无优劣，但 **golden、设备读 GM、多核分片** 必须同一约定。换读者、换 \(K\)，只要约定写进 spec，**不必改融合架构**。

### 1.5 多核分片（与算法正交）

行 \(p\) 可分给不同 AIV；每个核握 \(\hat{s}[0..K-1]\) 的**完整副本**时，行 18 无需核间交换 \(\hat{s}\)。这是 **数据并行**，不是数学变化。

## 2. 流水线融合的工程不变量（芯片无关）

把 NTT 与内积合成 **单次设备驻留流水线** 时，下列不变量与 AscendC 无关，对任何「阶段 A 产出 → 阶段 B 消费」的 PQC 混合算子成立。

### 2.1 生产者–消费者契约

```
阶段 A（NTT 链）  ──写入──►  中间态缓冲区 B  ──读取──►  阶段 C（内积 / 矩阵乘）
```

- **B 在 A 与 C 之间应保持「权威副本」**：C 只从 B 读，不从「为 debug 写到别处的副本」读。
- 若 C 从 **另一存储层次**（如 GM 上的 debug dump）读，而 B 仍被后续写入，则 **语义上已不是同一次流水线的状态**，只是偶然数值有时相同。

**类比**：编译器中间 SSA 值在寄存器里，不应为了 printf 写回内存再让下一 pass 从内存读——除非你把那次写回 **定义为** 官方数据流。

### 2.2 「驻留」与「落盘」分离

| 类型 | 含义 | 生产路径是否允许 |
|------|------|------------------|
| **驻留** | 下一阶段的唯一输入源 | 必须是 UB（或等价 on-chip 缓冲） |
| **落盘** | 对拍、日志、host 可见 | 可在 **整段计算结束后** 写 GM |

**违反驻留**：A 结束立刻 `dump(B→GM)`，C 从 GM 读——即使结果有时对，也是 **绕路实现**，通常带来：

- 额外 MTE 带宽与 barrier；
- 第二次 launch 或第二次 kernel 调度；
- 性能数量级劣化（本案例：tick 从 ~65k 到 300k+）。

### 2.3 融合 vs 拆段

| 策略 | 优点 | 风险 |
|------|------|------|
| **单 launch 融合** | 少同步、中间态不离片内存储 | UB 预算、Init 布局一次算清 |
| **多 launch 拆段** | 每段 UB 小、易调试 | 必须定义 **段间 GM 契约**；不能声称「UB 融合」 |

调试可用拆段；**性能验收与生产语义**应对齐融合路径。

### 2.4 验证面递进（契约收窄）

对复合算子 \(F = G \circ H\)（例如 \(G\)=加噪声，\(H\)=内积）：

1. 先验证 \(H\) 单独正确（`golden_H`）；
2. 再验证 \(G \circ H\)（`golden_F`）。

**不要**在 \(H\) 的 SIM 未过前接入 \(G\)——否则失败时搜索空间是 \(F\) 全体，调试成本指数上升。

## 3. AscendC 上的通用实现模型

以下从 §2 的不变量 **落地到 AscendC**；换 \(N,K\) 仍成立。

### 3.1 存储层次与 TPipe

- **UB**：片内高速缓冲，由 `TPipe::InitBuffer` 在 **kernel 初始化阶段** 划分。
- **GM**：片外；带宽与延迟差数个量级。
- **每个 AIV 实例通常对应一个 TPipe 生命周期**：在同一 kernel 内 **再构造第二个 TPipe 并 InitBuffer**，在 cmodel/设备上常与已有 UB 布局 **重叠**，表现为 **无关阶段的数据同时被污染**（不仅当前算子错）。

**原则**：融合 = **一个 TPipe 规划整张 UB 地图**；子算子若需独立 TPipe，应 **另一次 kernel launch**，并在文档中写明 GM 段间契约。

### 3.2 ROM / LUT 尺寸跟「算法块度」走，不跟「别的阶段的 tiling」走

全长度 \(N\) 的 NTT 域 basemul，在 paired 形式下需要 **\(N/2\) 个 \(\gamma_i\)** 及配套的 gather / interleave 表。

- 正确尺寸：**\(\Theta(N)\)** 个 pair，与 **当前 basemul 的 poly 长度** 绑定。
- 错误做法：复用 **另一阶段** 为 half-NTT、limb merge 定义的 `pairCount = N/4`（当 \(N=256\) 时为 64），导致表只灌了一半——**向量路径静默算错**，标量 CPU 路径有时仍 PASS（因标量用另一套查表）。

**抽象规则**：每个使用 ROM 的算子，在 spec 里写清 **`rom_pairs = f(poly_degree)`**；Init 时 **禁止** 用无关字段凑数。

### 3.3 TBuf scratch 与 TQue：职责不同

| 机制 | 适合 | 不适合 |
|------|------|--------|
| **TBuf + 偏移** | 大块 scratch、多段临时向量 | — |
| **TQue** | 与 MTE/向量流水握手的 **少量** 队列 | 为每个中间数组各开一个 Que |

TQue 在平台上占用 **有限 event 槽**（本仓曾踩 8 槽上限）。**中间变量应主要靠 TBuf 切片**，不是「一路 GM 输入一个 TQue」。

**融合时**：后段算子（内积）的 scratch **与** 前段（NTT merge）的 scratch **分区**；Init 顺序宜 **小缓冲、关键常驻缓冲在前，大 scratch 在后**，避免地图被后续 Init 覆盖的耦合（具体偏移是案例细节，见 §6）。

### 3.4 CPU 孪生 vs 设备 / SIM

| 能力 | CPU debug | 设备 / SIM |
|------|-----------|------------|
| 标量 `GetValue` 模拟 | 可靠 | 不适用 |
| TQue + 硬事件 `WaitFlag` | **常不可靠** | 可靠（需配对） |
| 向量 basemul | 可用标量参考路径 | 应用向量内核 |

**原则**：golden 用 **数学参考（C ref）**；CPU 可走标量 **语义路径**；SIM 走向量 **性能路径**——**两路径应对同一数学契约**，而不是同一套微指令。

### 3.5 静默错误：比崩溃更危险

本类问题特征：

- 编译、launch 均成功；
- 输出 **像** 模 \(q\) 内的数，但与 golden 差若干千；
- 独立小内核 PASS，融合大内核 FAIL → 优先怀疑 **资源地图 / ROM 尺寸 / UB 别名**，而非「公式推错」。

## 4. 验证与性能方法论

### 4.1 性能指标不要混用

| 指标 | 度量什么 | 常见误用 |
|------|----------|----------|
| **SIM Total tick** | 指令级模型周期 | 与墙钟混谈 |
| **墙钟** | 用户等待时间 | 开着全量 instr trace 当「优化后」 |
| **分段 tick 之和** | — | **≠** 全链路 tick（融合省同步与 GM） |

验收红线应写清：**哪条 launch、哪段 pass、是否融合**。

### 4.2 阶段门（Stage Gate）

抽象为：

```
Gate-0: 单算子探针（仅 H）  →  golden_H
Gate-1: NTT 链（无内积）    →  golden_ŝ
Gate-2: 融合（H 消费 Gate-1 的驻留态） → golden_H
Gate-3: 加 G（噪声 / encode）→ golden_F
```

每一 Gate **只新增一个未知量**；失败时 **不回退到 Gate-0 之前的大规模搜索**。

本仓库用 `mixPass` 实现 Gate；换项目可用不同名字，**逻辑相同**。

### 4.3 尽早探测（Early Probe）

**原则**：每个 Gate 结束后，用 **O(1) 或 O(head)** 成本检查中间态（前若干个系数 / byte），再进入下一 Gate。

- 数学上：若 \(\hat{s}\) 已错，\(\widehat{A}\cdot\hat{s}\) 必错——不必等全 poly 对拍。
- 工程上：SIM 跑满再发现 t_hat 错，等于 **用小时级反馈学加法**。

允许：Process **结束后** dump 到 GM 供 host 脚本 head 比较。  
禁止：为早验而在 **生产者–消费者之间** 插入非权威的 GM 读路径（§2.2）。

### 4.4 Golden 的角色

- Golden = **I/O  oracle**（黑盒期望输出）。
- Golden **≠** 设备必须逐步复制的参考源码。
- 设备可用不同分核、向量 basemul、UB 布局；**只要满足 §1 的数学与 §2 的不变量**。

## 5. 可复用模式目录（后续加解密）

### 模式 P1 — 单算子探针（Isolated Kernel Probe）

**问题**：混合算子难调试。  
**做法**：在独立目录实现 **仅 H**（如仅 NTT 域内积），瘦 UB 地图，CPU+SIM 对拍。  
**出口条件**：golden_H PASS + 记录 tick 锚点。  
**禁忌**：未过探针即粘贴进融合类。

### 模式 P2 — UB 驻留流水线（Resident Pipeline）

**问题**：NTT 后立即矩阵乘 / 内积。  
**做法**：NTT 输出写入命名 UB 区；下一阶段 **只读该区**；常量矩阵（公钥 \(\widehat{A}\)）可从 GM 读。  
**不变量**：§2.1–2.2。  
**禁忌**：中间 dump 到 GM 再读回算「融合」。

### 模式 P3 — 单 TPipe 地图（One Allocator）

**问题**：融合后静默错。  
**做法**：绘制 UB 地图（常驻 | 阶段 A scratch | 阶段 B scratch | ROM）；**一次 Init**；子算子不另建 TPipe。  
**检查**：ROM 条目数 = \(g(N_\text{basemul})\)，不借用别阶段的 count。

### 模式 P4 — 双路径语义等价（Twin Path）

**问题**：CPU 调试与 SIM 性能路径分歧。  
**做法**：CPU 标量语义路径 + 设备向量路径；共用同一 golden。  
**禁忌**：强迫 CPU 跑完整 TQue+硬事件向量路径。

### 模式 P5 — 验证金字塔（Verification Pyramid）

```
        [ 全协议 / encode / decaps ]
              /              \
      [ +噪声 G ]          [ 多密钥 ]
            /                    \
    [ 内积 H only ]          [ NTT only ]
```

每一层新增 **一个** 算子或 **一种** 数据；失败时 **落在当前层排查**。

### 模式 P6 — 性能回归先查数据流

tick 暴涨时按序查：

1. 是否多了一次 GM 往返？
2. 是否多了一次 kernel launch？
3. 是否全量 profiling 未关？
4. 最后才查微指令 / basemul 变体。

### 6.2 案例中的不变量落地

- 中间态 \(\hat{s},\hat{e}\) 在 `ub_ntt`；\(\hat{t}\) 在 `ub_that`。
- \(\widehat{A}\) 行主序读 GM；S3 与行18 **之间**不写 GM。
