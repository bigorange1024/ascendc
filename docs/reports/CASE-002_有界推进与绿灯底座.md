# CASE-002：有界推进与绿灯底座

## 基本信息

- 日期：2026-07-29
- 汇报对象：高层领导（合稿短讲）
- 使用场景：AI 辅助硬科技预研方法论合稿汇报（约 4–5 页正文，不含封面）
- 材料形式：封面 + 5 页 PPT
- 验收结果：合稿提案已定稿归档（待正式汇报）
- 终稿：[`汇报_有界推进与绿灯底座_v4提案.pptx`](汇报_有界推进与绿灯底座_v4提案.pptx)（本仓 `docs/reports/`）
- 归档内容：终稿、关键过程稿、全页预览

## 核心目标

说明在硬科技预研中如何先管住 AI，再有界推进：用「绿灯底座 × 缺项里补 × 先表后码」约束 Agent；用具体实例和图示对照回答「用了 AI / 用对 AI」的差别，并抽出可迁移规矩。

## 修改过程

### 初稿主要问题（领导反馈）

- 缺少具体实例，内容显得泛泛而谈；建议用图而不是长文给实例。
- 最重要的点是：用了 AI 和没有用（或没用好）AI 的比较。
- 要能抽象出方法论，引导其他工作。

### 关键修改

1. 叙事改为：疼一下（开放 AI 的代价）→ 给方法（一张图）→ 看实例（能力拓扑补全）→ 看对照（性能 + 配额）→ 能带走（五条规矩）。
2. 第 3 页做成具体案例拓扑：单点能力 → PKE.KeyGen → 识别收尾接缝缺项 → 补齐 → KEM.KeyGen；并对照 A 开放探索 / B 有方法论。
3. 第 4 页主视觉改为条形图，不再用大方框堆文字：
   - 上：单 AI Core 上单个 ML-KEM 解封装算子 cycles（A / B / C）
   - 下：月配额占用（A / B）
4. 术语降级：少讲 CT / PermitCode，多讲绿灯、缺项、禁止项、先表后码。

### 口径澄清（归档时确认）

- **月配额对照（A ≈ 2/3 vs B <5%）**：两边都是做 **Decaps 单算子**，属于**同任务严格对账**，不要写成「非同任务严格对账」。
- **算子性能（cycles）**：A / B / C 同为单算子 Decaps 口径；A 为 correctness 多段 launch 合计量级（示意 >150 万），B ≈ 1050646，C ≈ 1041906。
- **整套 ML-KEM**：可作为 B 路线的后续范围扩展说明（绿框），不要与上方「单算子配额 <5%」混成同一行数字。
- 不作未经对账的倍数宣称；性能胜场不是方法论相对 C 的主张（B ≈ C 同量级）。

## 最终结构

1. 封面：有界推进与绿灯底座；三词：绿灯底座 / 缺项里补 / 先表后码
2. 为什么必须先谈方法：开放自搜的三类失败 + 真实伤疤
3. 方法一张图：绿灯 × 缺项 × 禁止项 × 合法拼装 → 先表后码
4. 具体实例：单点 → PKE.KeyGen → 缺项 → KEM.KeyGen；A/B 泳道对照
5. 对照：Decaps cycles（A/B/C）+ 同任务配额（A/B）+ 四维表（正确性 / 性能 / 可交付 / 可迁移）
6. 能带走：适用场景 + 五条规矩

## 通过/定稿原因分析

1. 直接回应领导三点：有实例图、有 AI 对照、有可带走的方法。
2. 对照页用条形图而不是方框堆文，反差一眼可见。
3. 配额与性能都钉在同一检验床（Decaps），口径清晰。
4. 方法页去掉过重形式化术语，适合高层短讲。
5. 末页把资产写成规矩与习惯，不绑定某一版源码或平台。

## 可复用结论

- 高层短讲优先：「代价 → 方法一张图 → 实例图 → 对照图 → 可带走规矩」。
- 对照页至少同时回答：运行结果差多少、研发代价差多少、交付范围差多少。
- 同任务对账的数字，口径句里要写清「比的是什么」；扩展成果另起一句，不要挤进同一根条。
- 方法主张写「作业面被限制」，不写「Agent 变聪明 / 魔法提速」。

## 适用性限制

本案例针对合稿短讲与硬科技预研方法叙事；正式高层会后的验收结论待回填。一次定稿不能直接推广为所有管理层偏好。
