# 教材与调研文档写作指导

> **用途**：归纳维护者对 `docs/research/`（尤其形式方法教材草案）的文风、图示与修订偏好，供后续 Agent / 协作者改文档时对照。  
> **范围**：以教材长文与同目录调研稿为主；定稿技术总结另见 [`docs/notes/技术总结写作模板.md`](../notes/技术总结写作模板.md)。  
> **维护**：每确认一个**大版本**（如整章成文、图示体系重画、文风通改）后，把当次稳定下来的意见**追加/修订**进本文，并在文末「修订记录」留一行。  
> **当前文档思路**：可暂时保留；本指导记录的是「怎么写/怎么画」，不强制推翻已成文章节的叙事结构。

**最后刷新**：2026-08-20（第1章绪论 / 摘要文风；禁翻译腔与工程黑话；Ascend 字体）

---

## 1. 文风

| 偏好 | 说明 |
|------|------|
| **像讲课，但用正常中文** | 短句、主动语态、少堆名词化。像讲课 ≠ 把 `qa/` / Rule 里的工程黑话搬进教材。 |
| **去翻译腔（硬门禁）** | 避免「进行…操作」「基于…的情况下」「值得注意的是」等空转套话；也避免英文概念硬译（见 §1.1）。能说人话就说人话，学术表述用「结论 / 尚未证明 / 同量级」等，不用机翻词。 |
| **先讲清要传达什么** | 段首或图前用一两句点明本节在说什么；不要先铺术语再揭底。 |
| **结论与证据分开** | 结论用清楚的状态表述（有条件完成 / 未能证明 / 过程更可控）；证据指向章号、`qa/`、对照表、git，不靠形容词加油。 |
| **不吹过头** | 名实不符的通过未消尽、相对人工主线无性能优势、token 无严格对账——该写「没证明」就写，不把面积或棒长神话成全面胜利。 |
| **术语稳定** | 同一概念固定一种叫法（如闭包表、禁止项、对拍）；中英混用时专名保持可检索。 |

### 1.1 翻译腔与工程黑话：教材正文禁用

下列词在 `qa/`、Rule、合稿 PPT **内部**可用；**教材 / 摘要 / 绪论**须换成正常中文。

| 禁用或慎用 | 问题 | 教材改写示例 |
|------------|------|----------------|
| **检验床 / 压力测试床 / testbed** | 英文硬译 | 「用来检验方法的具体工程任务」「我们在…上做实验」 |
| **试金石** | 文言套语 / 翻译腔 | 「验证案例」「前瞻实例」 |
| **钉死 / 写死** | 口语黑话 | 「事先确定 / 事先约定 / 固定」 |
| **判决 / 已判定** | 法庭味，非教材常用 | 「结论 / 已有证据支持」 |
| **假绿** | 仓库黑话 | 「名实不符的通过」「表面通过、实际未满足验收」 |
| **强成功 / 弱成功** | 内部状态词 | 「相对开放探索，目标基本达成」「有条件完成」 |
| **作业面 / 受控搜索 / 开放空间 / 幻觉空间** | 英文直译堆砌 | 「允许做的事」「只在已验证能力上按规定推进」「不加约束的探索」「无效搜索」 |
| **对号入座** | 口语套话 | 「对照自身经历」 |
| **死路当捷径** | 语义不准 | 「死路仍当活路」：已走不通或已关闭的路线，仍被当作需要继续尝试的技术路线 |
| **臂 / 插槽** | 非中文教材常用 | 「路线」「实机档位 / 实机栏」 |

**合稿短讲（v4）可用口语**：绿灯底座、缺项里补、先表后码、伪完成——教材绪论可沿用这些**完整句**，但不要整章堆内部缩写（CT、PermitCode 等留给后文章节定义后再用）。

### 1.2 「口语教材」≠「仓库日志」

| 可以 | 不可以 |
|------|--------|
| 短句、主动语态、先给结论再展开 | 把 INDEX / customspec / incubating / launch 预算当正文默认词汇 |
| 用一件具体事例**立刻抽象**成问题类型 | 大段「device 先绿、STATUS 后补」——外行读不懂 |
| 读者从**需求**出发（谁有同样痛点） | 读者画像写成「需要搞懂仓库里一堆文件的人」 |

### 1.3 目标 vs 过程

- **目标**：想做成的事（例如：在 Ascend AI Core 上用 AscendC 实现可验收的 ML-KEM 能力）。  
- **过程**：incubating / stable、探针、波次编号——是实现路径，**不是目标**；外行也不关心。绪论 / 摘要里不要把过程阶段写进「目标」段。

## 2. 字体与专名（硬门禁）

| 规则 | 说明 |
|------|------|
| **禁止写「昇腾」** | 当前教材 CJK 字体（Fandol）缺「昇」(U+6607)，PDF 会缺字。统一写 **Ascend**（如 Ascend AI Core、AscendC）。已多次强调，写码/写文前自检。 |
| **平台名** | AscendC、AI Core、CAModel、SIM 等专名保持英文可检索形态。 |
| **算法实例** | 正文可用 ML-KEM；摘要 Key words 可用更宽的 **PQC**（与用户定稿一致）。 |

## 3. 绪论 / 摘要写法（2026-08-20）

| 项 | 要求 |
|----|------|
| **主矛盾对齐 v4** | 「终点已确定、路线不规定」；AI ≠ 自动加速；三类失败：死路仍当活路 / 仿真通过当终审 / 结果碰巧对（伪完成）。真问题是「用 AI 之前有没有边界」，不是「要不要用 AI」。 |
| **摘要结构** | 问题 → 方法（语言描述三件工具各管什么，**不堆公式**）→ 效果分维（相对开放探索 / 相对人工主线）→ 尚未证明 → 一句收束。 |
| **绪论不写公式** | 依赖闭包、合法拼装、作业过程只预告功能；符号与定义从第3章起。 |
| **效果不吹满** | 过程可控、配额同任务可对账处才写；相对人工主线写「同量级、未能替代」；token 不作未审计倍数。 |
| **标题页** | 作者 Ye Yuan；邮箱；摘要下 **Key words**；不要写仓库分支名作副标题。 |

## 4. 图示总原则：先想清楚图在说什么

**不要为画图而画图。** 动笔前先回答：这张图要传达什么**非图表难以一眼看出**的东西？

| 若要传达… | 可考虑… | 通常不必画成… |
|-----------|---------|----------------|
| 多父依赖、接缝汇合 | DAG / 分层依赖图（折线箭头） | 把对拍材料、禁止项文书塞进同一张实现依赖图 |
| 泳道之间的禁抄、复用、共享终态 | **跨道有关联**的泳道图 | 三条互不相干的单线串行 |
| 集合重叠 / 共有终态 | 欧拉图或明确的「共享锚点」 | 三列口号列表冒充对照 |
| 时序依赖、先后约束 | 时序图或概念分层 | 「①→②→③→④→⑤」流水线复述正文枚举 |
| 多维开销/负担形态 | 雷达图（轴名为中性量） | 人为二元门禁项的条形图 |
| 自然可感的量（tick、速度、大小） | 条形图 / 棒图 | — |

**单线串行**（正文枚举已经说清的步骤链）→ **默认不画流程图**。若仍需给读者「分层/角色」感，优先用**概念目录树**（见下节），而不是盒子箭头。

## 5. 依赖图与箭头

| 规则 | 说明 |
|------|------|
| **只放实现相关节点** | 对拍用 KeyGen/Encaps、禁止项 vendor、「禁止抄码」文书等写在正文，不塞进实现依赖图。 |
| **折线 / 正交优先** | 避免斜线交叉重叠；必要时自左向右分层（模块 → 接缝 → 目标）。 |
| **分叉要干净** | 合法/拒绝等末级分叉：先共用竖段再左右折，避免两根 `|-` 重叠成一团。 |
| **冗余直连慎画** | 若模块→接缝→目标路径已表达依赖，外侧大跨度直连易制造交叉，宁可用分层布局。 |

## 6. 概念目录（替代无信息量时间轴）

当「先表后码 → 探针 → 研究副本 → 定型」只需表达**角色分层与先后**时：

| 做 | 不做 |
|----|------|
| 示意根名 + `01-…` / `02-…` 式概念层 | 在图里写死仓库真路径（`examples/incubating/exp-…`）→ 改为「不要把仓库真路径写进图」 |
| 图注标明「非仓库真路径；只读角色与先后」 | 把日后可能改名的目录字面量写进教材当真理 |
| 用注解标「最先落：闭包表」等 | 再画一条与正文重复的单线时间轴流程图 |

读者不关心真实工程目录细节；真路径放 `qa/` / `STATUS` / 对照表即可。

## 7. 指标与可视化

### 7.1 条形图 vs 雷达图

| 形式 | 适合 | 不适合 |
|------|------|--------|
| **条形 / 棒图** | 自然界或工程上可具象的量：SIM tick、时延、体积、条数——长短方向读者直觉清楚 | 人为发明的二元门禁、极性混杂的「得分」 |
| **雷达图** | 多维**形态**对照（开销结构、能力剖面）；看形状与面积 | 把「先表后码=0/1」等门禁项硬塞成轴再比面积 |

门禁二元项（先表后码、拦住非法、可交付、失败路径、名实不符通过的次数）→ **留在对照表**；不要仅为「也有五个数」就画条形图。

### 7.2 轴名必须是中性「量名」

类比足球经理（Football Manager）球员雷达：**防守 / 速度 / 精神**——只有量，没有评价前后缀。

| 禁止出现在轴名里 | 应改成量名示例 |
|------------------|----------------|
| 多、少、大、小、高、低 | 搜索空间（不是「搜索空间克制」） |
| 克制、不靠、优化后的… | 整路返工、资源空转、禁源依赖、前置文书 |
| 「小某某」「少某某」却把条画很长 | 读者会陷入「小某某不太小」的怪读法 |

### 7.3 极性写清楚

轴名中性之后，**必须在图注写明读法**，二选一、不要混用：

| 类型 | 读法 | 例子 |
|------|------|------|
| **开销 / 负担雷达** | 越大＝该量越大；**面积大＝负担更重** | A 搜索/返工铺开；B 收小、只在前置文书凸出 |
| **能力雷达** | 越大＝该能力越强；面积大＝整体更强 | 仅当轴本身是能力量且「多即好」 |

同一张图禁止一半轴「越长越好」、一半轴「越长越差」（旧五指标条形图的问题）。

### 7.4 示意与计量

| 规则 | 说明 |
|------|------|
| **序数示意要标明** | 无对账的 token、探索发散等，写「序数示意，非计量」 |
| **不写未对账倍数** | 五指标对照约定：两侧均不比 token 倍数；图上也不要假装有精确比 |
| **诚实折损** | 若 B 多付前置文书，开销雷达上应让「前置文书」轴 B 更长，不要为了「B 全面更优」抹掉代价 |
| **同任务对账写清口径** | 配额/性能比什么要写清（如「同为 Decaps 单算子」）；扩展成果另起一句，不要挤进同一根条（见 CASE-002 v4） |

## 8. 与仓库其它规范的边界

| 本文档管 | 不管 / 另有出处 |
|----------|-----------------|
| 教材与 `docs/research/` 调研稿的叙述与图示口味 | AscendC 写码门禁、customspec、frozen → `.cursor/rules` |
| 大版本后的文风/图示经验沉淀 | 定稿 notes 结构 → `docs/notes/技术总结写作模板.md` |
| 图「传达什么」的方法论 | 密码学正确性论证本身 |
| 教材用语（禁用检验床/假绿等） | `qa/` 日纪要可用内部黑话，**不要回灌教材** |

合稿短讲口径：[`docs/reports/CASE-002_有界推进与绿灯底座.md`](../reports/CASE-002_有界推进与绿灯底座.md)、v4 PPT。领导短讲与同事向数学讲义**分轨**，勿把 v4 直接加长塞公式。

## 9. 大版本更新清单（改文档收尾时勾）

1. 当次稳定的新偏好是否已写入本文对应节（文风 / 字体 / 图示 / 指标）？  
2. 若推翻旧约定，是否改掉本文过时句子，而不是只追加矛盾条？  
3. 文末「修订记录」是否留了日期 + 一句话？  
4. [`docs/research/INDEX.md`](INDEX.md) 是否仍指向本文？  
5. 当日 `qa/YYYY-MM/` 纪要是否链到本文（可选，重大口味变更时建议写）？  
6. 教材 PDF 是否扫过「昇腾 / 检验床 / 假绿 / 写死」等禁词？
