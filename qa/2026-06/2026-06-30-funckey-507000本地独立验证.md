## 4. 结论 + 实现守则

1. SIM AIV-only 核总数 **≤ 5**；想 launch 的核须落 `func_key ≤ 4`（按 `nm device_aiv.o` 复核）。
2. `func_key` 由 ascendc 编译期分配，不按源码定义序，**不能靠重排 cpp 顺序控制**；唯一可靠手段是减少 AIV-only 核数。
3. CPU build 独立 binary、func_key 无意义；CPU-only 核（如 `g3_linear`/`at_r`/`pack` 等可走 host 标量替代的部分）以 `#ifdef ASCENDC_CPU_DEBUG` 守卫，或在 CMake KERNEL_FILES 中按 RUN_MODE 选择性排除。
4. 「在 MIX 之后才 launch 的 AIV-only 核」可能另有 `107000`（AIV binary 注册失效）问题（家里 agent 注释中提到，本地暂未独立复现）；解法是声明为 `MIX_AIC_1_2` 占位（仅 SIM/NPU），CPU 保持 `AIV_ONLY`。
5. host↔device 往返打包前**必须** `aclrtSynchronizeStream(stream)`（家里 agent 病根 2，与本议题正交，待本地再验证）。

## 9. 排查过程回顾（错误尝试 ↔ 正确路径）

把这次 SIM「终于跑通」的来龙去脉按时间线和判读类型整理，避免后续探针重复同一类反模式。完整原理总结搬到 [`docs/notes/AscendC-CAModel-SIM-funckey与单session约束知识库.md`](../../docs/notes/AscendC-CAModel-SIM-funckey与单session约束知识库.md)，这里只列**人**层面的判读演化。

### 9.1 错误尝试（2026-06-19 ~ 2026-06-29）

| 编号 | 当时的判读 | 实际操作 | 错在哪里（事后回看） |
|------|-----------|---------|------------------|
| E1 | `f203_encrypt_t_dot_r` 单独 launch 失败 → 「该入口 SIM 注册失效」 | 用 `at_r(t̂_col0)` 等价绕开，写进 `G3_SIM_AUDIT §3.1 / §8` | 没看 `nm` `func_key`；把核数边界当成「核本身有问题」 |
| E2 | `f203_encrypt_g3_linear` 五参 launch 失败 → 「五 GM 指针 ABI 不兼容」 | 退化为两次 `at_r` 独立 session | 同 E1；五参 ABI 没问题，问题是 `func_key ≥ 5` |
| E3 | 两个 `at_r` 独立 `aclInit / aclFinalize` 「在 CANN 9.0 SIM 上是必需的」 | 写进 `G3_SIM_AUDIT §9.7` 作为「SIM 多 session 工程模式」 | 多 session 本身是 R2（同步）触发面；之所以「能跑」纯粹是因为每次 ACL 重载会重新分配 `func_key`，第二次 `at_r` 有时落到 ≤4 |
| E4 | `f203_encrypt_g4_noise` / `pack` SIM launch 507000 → 「这两个核 SIM 不支持」 | 降级为 host scalar G4 tail（`f203_encrypt_g4_host_scalar.hpp`、`f203_encrypt_pack_host_scalar.hpp`），写进 STATUS「混合路径」 | 这两个核没坏，`func_key=8/11` 全踩 R1 边界 |
| E5 | SIM 末尾偶发 `free(): invalid pointer`「疑 ACL 多段 Init/Finalize 副作用」 | 列为 STATUS 遗留事项，未推进 | 单 session 后此现象消失，本质就是 R2 |
| E6 | 「`c.bin` 字节对了就 PASS」 | 仅以 SIM `c.bin max=0` 收尾、未做单步 funckey 排查 | CPU 孪生 PASS 也只保证算法正确，没有暴露 R1；R1 必须用 `nm` + 受控实验暴露 |

**共因**：所有 E1–E5 都是「把 R1 边界（核数）造成的失败，错认成核本身/入口/ABI/Init 流程问题」，每次都换一种 workaround，却没追到「单 binary 只能容 5 个 AIV-only」这个共同上限。

### 9.2 正确路径（2026-06-30）

| 步骤 | 内容 | 关键证据 |
|------|------|---------|
| C1 | 家里 agent 在 `27cc93b` 用对照实验提出 R1 命题 | [`AGENT_HANDOFF.md`](../../AGENT_HANDOFF.md) §SIM 507000 病根 |
| C2 | 本地拒绝 pull、改在原探针做**正向证伪**实验：`F203_FUNCKEY_EXPERIMENT` CMake 开关 | §3 |
| C3 | `nm device_aiv.o`：边界 4↔5 在 12 个 AIV-only 核上完美对齐 | §2 表 |
| C4 | 同一份 `f203_encrypt_g4_noise` kernel：默认 build `func_key=8` 时 507000 / 实验 build `func_key=4` 时 ret=0 | §3.3 |
| C5 | R1 坐实后，**结构性**重做 G3：`at_r5` 合并核（kP=5）一次出 `[û \| tr̂]`，host 拼 `matM`；prep+NTT+decode+at_r5 装进**同一** ACL session | §8.1 |
| C6 | 双模式 `ENCRYPT_VERIFY=1` 双 PASS（max=0 1568 bytes），host binary `nm` 无残留死引用 | §8.2 |
| C7 | 旧错误路径的 4 个 G3 核从 `KERNEL_FILES` 永久剔除；源文件保留为历史证据；`F203_FUNCKEY_EXPERIMENT` 守卫永久保留（默认 0） | §8.1 / CMakeLists `KERNEL_FILES` |

**判读差别**：C1–C7 始终把假说写成「同一份代码 + 不同 KERNEL_FILES → ret 不同」的可重现实验，避免再次把现象归因到 kernel 本身。

| `wall_sec`（含 build + verify）| 367 s（STATUS 旧表）| **334 s** | -9%；省在不再启第二个 ACL session |
| AIV-only 核数（SIM device_aiv.o） | 12（含 g3_linear / g3_linear4 / at_r / t_dot_r 4 个）| **9** | 留出 3 个名额，至少 1 个用来未来把 g4_noise / pack 升 device |
| G4 tail（INTT 后噪声+pack） | INTT device + 噪声/pack host scalar | 同左（尚未 device 化） | 没改变；属下一步 P2/P4 工作 |

性能解读：
- tick 减半是**结构性**收益（一次 launch 替代两次），不是 vector 路径加速。
- 单 launch 内 `at_r5` 多算 1 个 `tr̂` 行（kP=5 vs kP=4），但与「launch 启动 + binary 装载 + 第二次 ACL session」的开销相比可忽略。
- `wall_sec` 改善主要来自跳过第二个 `aclInit/aclFinalize` 循环；build 段时间相同。

## 11. 经验教训（迁移到后续探针）

> 这些是「下次设计 SIM 算子时**先**想到、而不是踩坑后才想到」的清单。完整原理沉淀在 [`docs/notes/AscendC-CAModel-SIM-funckey与单session约束知识库.md`](../../docs/notes/AscendC-CAModel-SIM-funckey与单session约束知识库.md)。

| L | 内容 |
|---|------|
| **L1** | SIM 上 `507000` **第一反应**：`nm device_aiv.o` 看 `func_key`，再看是不是单 session。算法 / 入口 / ABI 留到最后查。 |
| **L2** | AIV-only 核数 ≤ 5 是**设计期资源**，不是事后优化对象。开新算子前先列「目标 AIV 核清单 + `func_key` 名额」。 |
| **L3** | 「同一阶段拆 4 个小 kernel 更容易实现」是反模式。能合并到一次 launch 就先做；剩余复杂度可以靠 host 拼装吸收（P3）。 |
| **L4** | `aclInit / aclFinalize` 在一次推理内**只一次**。任何「调试时先开第二个 session 验证一下」的代码都不要留到主路径。 |
| **L5** | 每次 `aclrtMemcpy(... DEVICE_TO_HOST)` 之前**显式** `aclrtSynchronizeStream`，不靠 launch 返回 = 完成的错觉。 |
| **L6** | 受控实验代码（如 `F203_FUNCKEY_EXPERIMENT`）默认 OFF + 永久保留，不要因为「实验结束」而删干净 — 病根的可重现实验比文档管用十倍。 |
| **L7** | CPU 双模式 PASS **不能**代表 SIM PASS；CPU 不暴露 R1/R2。任何「SIM 跑通」声明都要附 `nm` 结果与单 session 证据。 |
| **L8** | 当怀疑某 kernel 是 R1 受害者时，**临时把它从 `KERNEL_FILES` 移除**并跑一次 — 若该核之外的其他 kernel 重新 PASS，就坐实了 R1 共因。 |
| **L9** | 错误判读会写进文档（如 `G3_SIM_AUDIT.md`），后人看到时会被误导。改对之后**不要删原文**，而是加 supersedence 段，让历史可读、可学。|
| **L10** | 性能比较只用 `Total tick`，不用 `wall_sec`；wall 含 build / verify / python，跨 build 不可比。 |

## 16. PKE device Encrypt→Decrypt round-trip（2026-06-30 夜）

**背景**：各探针 `run.sh` 单独验收时，Decrypt 的 `c.bin` 来自 host `golden_c.py`，**非** device Encrypt 产出；缺少 **KeyGen 密钥 + device c → device m** 闭环证据。

**交付**：仓库根 [`scripts/roundtrip_pke_encrypt_decrypt.sh`](../../scripts/roundtrip_pke_encrypt_decrypt.sh)（编排）+ `roundtrip_pke_prepare.py` / `roundtrip_pke_verify.py`。

| 项 | 内容 |
|----|------|
| 密钥来源 | [`pass-fix-f203-alg13-device-keygen-k4`](../../ascendc-tests/ml-kem/ml-kem-1024/pass-fix-f203-alg13-device-keygen-k4/) `output/ek_pke.bin` + `dk_pke.bin`（**不**重复跑 KeyGen，除非 `ROUNDTRIP_BOOTSTRAP_KEYGEN=1`） |
| 明文 / coins | `SEED_D=20260619` + 991（与两探针 `gen_data` 同规则） |
| 对拍 | `ENCRYPT_VERIFY=0` / `DECRYPT_VERIFY=0`；`m.bin` vs Encrypt `input/m.bin`，**非** host golden |
| cpu/sim 二进制 | `_build_case` 按 `RUN_MODE` 戳记 `.roundtrip_built_mode`，切换模式自动重编 |

**验收命令**：

```bash
bash scripts/roundtrip_pke_encrypt_decrypt.sh -r cpu -v Ascend910B4
SIM_DIRECT=1 bash scripts/roundtrip_pke_encrypt_decrypt.sh -r sim -v Ascend910B4
```

**结果（本机 2026-06-30）**：

| 模式 | Encrypt kernel | Decrypt kernel | 对拍 |
|------|----------------|----------------|------|
| CPU | ~8–9 min（tikicpu） | ~3–4 s | **max=0**（32 B） |
| SIM | wall ~633 s | wall ~253 s（tick ~427k） | **max=0**（32 B） |

日志：`[SUCCESS] round-trip PKE Encrypt→Decrypt (cpu|sim) SEED_D=20260619`；Decrypt 侧 stray dump 已收拢至 `sim_log/`。

**结论**：device **c** 经 device **Decrypt** 还原 **m** 与 Encrypt 明文一致；补全单探针 host-golden 之外的跨算子闭环。**关闭 T16**。
