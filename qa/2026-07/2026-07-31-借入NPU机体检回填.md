## 10. 实机首轮反馈：msprof 无产物 + Encrypt gen_data 挂（同日续）

### 10.1 `RUN_WITH_MSPROF=1` 在 ML-KEM 探针上无效

**现象**：实机 `RUN_WITH_MSPROF=1 bash run.sh -r npu`（PKE KeyGen）不产任何 `OPPROF_*`。

**根因**：该变量**只有 `ascendc-tests/add_custom/run.sh` 实现**；ML-KEM 各探针 run.sh 一律
`bash scripts/kernel-run-timeout.sh <bin>` 直跑，未使用的 env 被 shell 静默忽略。**非环境问题**。

**处置**：抽出共用包装 **[`scripts/msprof_run.sh`](../../scripts/msprof_run.sh)**（函数 `msprof_run_kernel`）：

| 条件 | 行为 |
|------|------|
| 默认（`RUN_WITH_MSPROF` 未设 / ≠1） | **逐字等价**原 `kernel-run-timeout.sh` 直跑；**不产** prof/OPPROF |
| `RUN_WITH_MSPROF=1` + `-r npu` | `msprof op <bin> --output=<用例>/prof_npu/<bin>/` |
| `RUN_WITH_MSPROF=1` + `-r sim` | `msprof op simulator … --soc-version=…`（很慢） |
| `RUN_WITH_MSPROF=1` + `-r cpu` | 告警并退回直跑（CPU 孪生无硬件计数器） |

产物只落 `prof_<mode>/<bin>/`（`OPPROF_*` 在其内），用例根不留 stray；按二进制分子目录，
Decaps 的 D/E 两 phase 各自留档。已接入 **PKE×3 + KEM×4** 七个探针，run.sh 头注释标「非默认」。

### 10.2 实机 Encrypt 失败：`pathlib.read_text` FileNotFoundError

**现象**：KeyGen / Decrypt 实机通过，**Encrypt 挂在 `gen_data.py`**，日志含 `correctness 缺失`
与 `pathlib.py … read_text`。

**根因（本轮 §8 引入的回归）**：`alg14` 的 `host_golden/f203_ref_common.py` 被改成从**仓库根**
`thirdparty/ntt_onnx/` 取 `transpose_mlkem_luts_i8.h`，而该目录是**私有仓 clone、不入 git**。
WSL 因 `input/lut_*.bin` 是旧产物、`gen_data` 命中缓存路径而未暴露；实机 `input/` 干净 → 直接崩。
KeyGen / Decrypt 用的是**探针内 vendored 且随 git 分发**的同名头，故不受影响。

**处置**：`_resolve_lut_hdr()` 三级候选（首个存在者胜）——`F203_LUT_HDR` env → 仓库根私有
`thirdparty/ntt_onnx` → **stable PKE KeyGen 交付树内 vendored 副本（随 git 分发）**；三者皆无时
报明确错误而非裸 `FileNotFoundError`。验证：临时移走 `thirdparty/ntt_onnx` + 清空 `input/golden`
后重生成，四个 LUT bin 与 `golden/c.bin` 与私有仓路径产物**逐字节一致**。

**顺带**：`gen_data.py` 的 `_CORR` 自 ml-kem 目录重排后一直指向不存在的
`ascendc-tests/ml-kem/examples/stable/…`（用户看到的「correctness 缺失」即此）。改为仓库根正确
路径，但**复用默认关闭**（`ENCRYPT_REUSE_STABLE_INPUT=1` 才开）——stable 树的 `input/` 是运行期
产物，roundtrip 脚本会写随机 fixture，默认复用会让本探针锁定的 `SEED_D` 语义漂移。

## 11. stable 七算子上机改造 + KEM golden 去 liboqs（同日续）

**触发**：用户要求「每个用例单独跑都要能跑通，且实机装不了 thirdparty 库」。范围从 7 个探针
扩到 **7 个 stable 算子**，并暴露出 KEM 侧的**第二类硬依赖**。

### 11.1 零 thirdparty 实测：PKE 全绿、KEM 全挂

移走 `thirdparty/` + 预编译 `scripts/liboqs_*_ref` 后跑 7 个探针：

| 组 | 结果 |
|----|------|
| PKE ×3（Alg.13/14/15） | **OK** —— §10.2 的 LUT 三级回退生效 |
| KEM ×4（Alg.19/20/21/21-ct） | **FAIL**，同一处：`gen_data` 调 `scripts/liboqs_kem_ref`，缺则 `build_liboqs_kem_ref.sh` → `missing thirdparty/liboqs/build/lib/liboqs.{so,a}` |

预编译的 `liboqs_kem_ref` 是 **x86_64 且不入 git**，实机 aarch64 也用不了。stable 四个 KEM 算子
走同一路径，同样会挂。

### 11.2 决策：liboqs 优先 + 回落仓内已验证参考（用户拍板）

关键观察：KEM 层相对 PKE 层只多**哈希与拼装**，计算内核仓里都有且都已对拍过 ——
`golden_c.golden_encrypt` 给完整 1568B 密文，`g_mh` 本来就同时算出 K（原代码只用了 coins），
拒绝分支 `J(z‖c)` 本就是纯 `hashlib`。故**不需要**动 `m=urandom` 等锁定参数即可闭合。

新增 **[`library/shared/f203_kem_ref/kem_ref.py`](../../library/shared/f203_kem_ref/kem_ref.py)**：

| 能力 | liboqs 路径 | 回落路径（无 liboqs） |
|------|-------------|----------------------|
| KeyGen | `liboqs_kem_ref keygen` | `ek_kem = ek_pke`；`dk_kem = dk_pke‖ek‖H(ek)‖z`（PKE KeyGen 借 stable KEM KeyGen 的 `keygen_golden`） |
| Encaps | `… encaps` | `(K,r)=G(m‖H(ek))`；`c=Encrypt(ek,m,r)`（`golden_c.golden_encrypt`） |
| Decaps 拒绝 | `… decaps`（仍做交叉） | `K=J(z‖c)`（SHAKE256） |
| Decaps 合法 | `… encaps/decaps` | 本地 encaps 同源；**外部 `C_SRC` 且无 `K_ENC_SRC` 不覆盖** → 给可操作报错 |

开关：`KEM_GOLDEN_BACKEND=python` 强制回落自检；`KEM_GOLDEN_CROSS=1` 两路逐字节互校。
实测 CROSS：KeyGen(ek,dk)、Encaps(c,K) **liboqs ≡ python**；固定 `M_HEX` 下 A/B 产物 `cmp` 一致。

### 11.3 第二个实机拦路石：密钥对 stash

四个 Decaps 用例默认读 `output/kem_keypair_stash/{ek,dk}_kem.bin`（**不入 git**），缺失时
`exit 2` 并提示跑 `kem_keypair_stash_bootstrap.sh`（而该脚本又指向已重排掉的旧 keygen 目录）。
处置：`kem_ref.bootstrap_keypair()` —— stash 缺失时按 `SEED_D`（缺省 20260619，与 KeyGen 用例
同值）derand 现造一对。**仅在原本会报错的路径生效**，不改变已绿场景；需固定钥仍可
`EK_KEM_SRC`/`DK_KEM_SRC` 或先跑 stash 脚本。
