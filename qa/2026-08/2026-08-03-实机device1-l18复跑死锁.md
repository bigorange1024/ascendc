# 2026-08-03 — 实机 device1 上 l18_l19 复跑死锁 · 默认 ASCEND_DEVICE_ID 改回 0

**主题关键字**：stable 七用例 · 第 2 次卡住 · `f203_encrypt_l18_l19` · CrossCore · **device 1 复跑挂 / device 0 可连跑** · 缺省设备号 1→0

---

## 1. 现象

借入 910B4 实机跑 1024 stable 七用例：

| 轮次 | 结果 |
|------|------|
| 第 1 遍全组 | 全绿 |
| 第 2 遍 | 加解密 / 封装解封装卡住；KeyGen 仍可过 |

卡点（host 已打印 launch、停在随后的 `aclrtSynchronizeStream`）：

- Encaps：`[kem-enc] launch 2 f203_encrypt_l18_l19 …` 之后
- Decaps-E：`[kem-dec-e] launch l18_l19 (inline pack + FO -> K)` 之后

共同点：都在 **MIX 核 `f203_encrypt_l18_l19`**（AIC↔AIV CrossCore FSM）；Encaps 无 FO/`SyncAll`，故病灶是 CrossCore 握手，不是 FO。

WSL 上同一 encaps **CPU 连跑两遍全绿** → 非 gen_data / 软链 / golden 回落问题。

## 2. 隔离实验（用户实测）

| 实验 | 做法 | 结果 |
|------|------|------|
| **A** | 默认设备（当时缺省 **1**）下 encaps 连跑两遍 | **第 2 遍卡住** |
| **B** | `ASCEND_DEVICE_ID=0` 连跑两遍 | **两遍都过** |

结论：**不是 l18_l19 算法逻辑在「第二次输入」上必然死锁**，而是 **物理 device 1**（或该卡 + CANN 9.1.0-beta.3 组合）在首轮 MIX 之后复跑会把 CrossCore 握手挂死；device 0 无此症状。

## 3. 处置

原先为「借入多卡避开物理 0」把 npu **缺省改成 1**，在本借入机上适得其反。

| 项 | 新约定 |
|----|--------|
| `run.sh` npu | `ASCEND_DEVICE_ID="${ASCEND_DEVICE_ID:-0}"` |
| host `main*.cpp` | `deviceId = 0`（仍可读 env 覆盖） |
| SIM | 不变，强制 `ASCEND_DEVICE_ID=0` |
| 需避让物理 0 时 | **显式** `ASCEND_DEVICE_ID=1 bash run.sh -r npu …`，并知该卡可能复跑挂 |

覆盖范围：1024 探针×7 + stable×7 + `add_custom` + `pass-toy-mix-s123-byteencode-k2`。
